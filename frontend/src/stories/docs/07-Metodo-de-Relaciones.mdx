# Método de Relaciones (paso a paso, sin magia)

Esta página explica **exactamente** en qué me basé para mapear archivos CSV -> tablas -> columnas -> relaciones.

## 1) Fuente de verdad usada

Tomé la relación desde estos archivos del repo:

- `etl/config/sources.py`: define cada fuente, nombre de archivo, tabla destino, `pk_cols` y `upsert_mode`.
- `etl/pipeline.py`: orden de carga y cómo se construyen dimensiones/facts.
- `sql/schema.sql`: estructura física de tablas, tipos y relaciones comentadas.
- `sql/looker_queries.sql`: joins reales usados en analítica.
- `backend/main.py`: endpoints para exponer metadata real de BD.

## 2) Cómo se infiere una relación lógica

Para cada fuente del ETL:

1. Leo `source_key` + `file` + `table` + `pk_cols`.
2. Verifico en `pipeline.py` qué columnas se convierten en claves de dimensión/hecho.
3. Cruzo con `schema.sql` para confirmar nombre de columna destino y tipo.
4. Valido en queries (`looker_queries.sql`) que el join se use de esa misma forma.
5. Marco confianza:
   - `high`: aparece consistente en `sources.py` + `pipeline.py` + joins.
   - `medium`: mapeo semántico (catálogo) sin FK física explícita.

## 3) Por qué “FK físicas” pueden ser pocas

En este proyecto, muchas relaciones se manejan como **lógica ETL** (por código y hash/upsert), no como `FOREIGN KEY` SQL estricta.
Por eso en la base real pueden aparecer pocas FKs físicas aunque haya muchas relaciones de negocio.

## 6) Regla práctica para auditar cualquier columna

Si alguien pregunta “¿de dónde salió `X`?”:

1. Buscar `X` en `etl/config/sources.py` para ubicar fuente y `pk_cols`.
2. Buscar `X` en `etl/pipeline.py` y transformers para ver limpieza/mapeo.
3. Verificar `X` en `sql/schema.sql` (tabla/tipo/nullable).
4. Confirmar uso en `sql/looker_queries.sql` o `frontend/src/components/QueryPresets.tsx`.
5. Validar en vivo en story `DB Real y Lineage`.
