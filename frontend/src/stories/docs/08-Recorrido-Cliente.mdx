# Recorrido Completo (vista cliente)

Este es el guion para mostrar el producto a un cliente final, de principio a fin.

## Objetivo de la demo

Mostrar que el cliente puede:

1. Entender rápidamente qué hace la solución.
2. Explorar tablas y estructura de datos.
3. Ejecutar consultas con seguridad (solo lectura).
4. Obtener resultados claros para negocio.
5. Confiar en el origen de datos y trazabilidad ETL.

## Duración sugerida

- Demo express: 10 minutos.
- Demo completa: 20-25 minutos.

## Paso 1: Portada y contexto (2 min)

Abrir `01. Documentacion > Introduccion`.

Qué ve el cliente:

- Qué es TEG SQL Explorer.
- Arquitectura general (CSV -> ETL -> PostgreSQL -> API -> UI).
- Flujo de consulta de extremo a extremo.

Mensaje clave:

- “No es solo una pantalla SQL; es una capa de validación y control de calidad sobre el ETL.”

## Paso 2: Modelo de datos (3 min)

Abrir `01. Documentacion > Schema de BD`.

Qué ve el cliente:

- Esquemas `cat`, `dim`, `fact`, `raw`, `etl`.
- Relaciones principales entre dimensiones y hechos.
- Tablas más importantes para análisis.

Mensaje clave:

- “Tus métricas salen de un modelo organizado: catálogo/dimensión/hecho, no de hojas sueltas.”

## Paso 3: Cómo se cargan datos (3 min)

Abrir `01. Documentacion > Pipeline ETL`.

Qué ve el cliente:

- Flujo de ingesta, validación y carga.
- Reglas de idempotencia (`hash`, `line_hash`, `upsert`).
- Orden de carga por fuente.

Mensaje clave:

- “Si el archivo no cambia, no se reprocesa. Si cambia, se actualiza de forma controlada.”

## Paso 4: API y seguridad SQL (2 min)

Abrir `01. Documentacion > API y Looker`.

Qué ve el cliente:

- Endpoints disponibles.
- Contrato de request/response.
- Restricción de solo lectura (`SELECT`, `WITH`, `EXPLAIN`).

Mensaje clave:

- “El usuario de negocio puede consultar, pero no romper ni modificar la base.”

## Paso 5: Verificación real de BD (4 min)

Abrir `01. Documentacion > DB Real y Lineage > Live`.

Qué ve el cliente:

- Conteos reales de columnas, relaciones físicas, fuentes ETL y CSV detectados.
- Tabla de `source_key -> archivo -> destino`.
- Relaciones lógicas documentadas con evidencia.
- Columnas reales traídas desde `information_schema`.

Mensaje clave:

- “Esto no está ‘hardcodeado’ para la demo: está conectado a la DB real.”

## Paso 6: Explicación didáctica de relaciones (3 min)

Abrir `01. Documentacion > Metodo de Relaciones`.

Qué ve el cliente:

- Cómo se deducen relaciones paso a paso.
- En qué archivos se basa cada inferencia (`sources.py`, `pipeline.py`, `schema.sql`, `looker_queries.sql`).
- Diferencia entre relaciones lógicas y FKs físicas.

Mensaje clave:

- “Podemos justificar cada columna y cada join con evidencia técnica del repo.”

## Paso 7: Experiencia de uso (UI real) (5 min)

Ir a `02. Componentes`:

1. `SqlEditor`:
   - Escribir consulta o usar SQL externo.
   - Ejecutar con botón o `Ctrl+Enter`.
2. `SchemaPanel`:
   - Navegar por esquemas/tablas.
   - Cargar consulta base al hacer clic.
3. `QueryPresets`:
   - Abrir categorías de consultas de negocio.
   - Seleccionar una consulta lista para usar.
4. `ResultsTable`:
   - Ver filas, columnas, tiempo de ejecución y truncado.
   - Visualizar estado vacío/error/datos.

Mensaje clave:

- “Un analista puede responder preguntas de negocio sin depender de ingeniería para cada consulta.”

## Paso 8: Cierre comercial

Checklist final para cliente:

1. ¿Puede confiar en la trazabilidad de cada dato?
2. ¿Puede auditar carga y calidad por lote?
3. ¿Puede autoservirse análisis con consultas seguras?
4. ¿Puede integrar las consultas en BI (Looker)?

Si las 4 respuestas son “sí”, la demo cumplió objetivo.

## Apéndice: Script corto (2 minutos)

Si tienes poco tiempo, muestra solo:

1. `Introduccion`
2. `DB Real y Lineage > Live`
3. `SqlEditor` + `ResultsTable`

Con eso el cliente ve: propósito, evidencia real y resultado operativo.
