Workbook A4F: Ingeniería de Contexto para el Diseño de Sistemas Agénticos
Versión: 2.1 (Iteración de Precisión)
Audiencia: Equipo de Desarrollo LLM (A4F)
Propósito: Estandarizar y aplicar nuestra metodología de Ingeniería de Contexto para construir, delegar y auditar sistemas agénticos de nivel de producción.
1. El Mindset A4F: De Asistente a Desarrollador SWE Asíncrono
El primer cambio es de mentalidad. Abandonamos el uso de LLMs como meros asistentes para consultas "naif" (ej. "explícame este error").
En A4F, tratamos a la IA como un Desarrollador de Software (SWE) Asíncrono. Nuestra tarea es conceptualizar y delegar desafíos técnicos completos (módulos, componentes de punta a punta) a un agente que opera con un contexto global híper-definido.
Para entender por qué esto es un game-changer, usamos esta analogía:
* El LLM (Large Language Model) es la CPU: El motor de razonamiento que maneja operaciones complejas.
* La Ventana de Contexto es la RAM: La memoria volátil y de corto plazo con la que trabaja el LLM.
* La Ingeniería de Contexto es el Sistema Operativo: Nuestra disciplina. Es el sistema que asegura que la información correcta y relevante (código, reglas, herramientas, memoria) esté cargada en la RAM en el momento preciso para que la CPU tome la mejor decisión.
2. Los 7 Pilares de la Ingeniería de Contexto
Nuestra "Ingeniería de Contexto" consiste en gestionar activamente los 7 componentes que el agente "ve" en cada paso de un flujo:
* User Prompt: El input inicial del usuario o del sistema que dispara la tarea.
* Instructions / System Prompt: Las directrices globales y del proyecto (ver Patrón de 8 Puntos). Guían cómo procesar la información.
* Long-Term Memory (Memoria a Largo Plazo): Datos persistentes útiles para tareas futuras (ej. Bases de datos vectoriales, RAG).
* State / History (Memoria a Corto Plazo): El estado actual de la tarea. Mantiene los datos necesarios ahora (ej. "el usuario ya se autenticó").
* Retrieved Information (RAG): Información específica recuperada de la memoria a largo plazo que es relevante para la decisión actual.
* Available Tools (Herramientas Disponibles): Funciones, APIs y herramientas externas que el agente puede invocar para operaciones complejas.
* Structured Output: La definición del formato de salida (ej. JSON, ZIP, XML) que el agente debe producir.
3. Arquitectura Operativa A4F: El Flujo Multi-LLM
No usamos un solo LLM para todo. Asignamos roles basados en fortalezas para ejecutar la delegación:
* El Arquitecto de Prompts (Gemini):
* Misión: Tomar un Metaprompt (la solicitud de delegación inicial del desarrollador humano) y transformarlo en un Máster Prompt (la instrucción final, estructurada y lista para el agente).
* Por qué: Usamos Gemini por su capacidad narrativa y su ventana de contexto masiva (1M tokens). Puede procesar el Metaprompt (que es más conversacional) junto con todo el código, las HUs, y los documentos adjuntos sin perder detalle, para generar el Máster Prompt estructurado de 8 puntos.
* El Desarrollador Cirujano (GPT-5 Pro / Razonador):
* Misión: Recibir el Máster Prompt (generado por Gemini) y ejecutar la tarea de desarrollo.
* Por qué: Aunque su ventana de contexto es menor, su cualidad es desarrollar mejor el código. Es el "cirujano" que se enfoca en la tarea híper-definida. Su entregable es el artefacto de software (ej. un .zip).
* El Auditor de Calidad (Modo Agéntico / Sandbox):
* Misión: Recibir el artefacto (.zip) del "Cirujano", desplegarlo en un sandbox seguro, ejecutar pruebas, encontrar errores y proponer correcciones.
* Implementación: Se logra con el "modo agéntico" de GPT-5 Pro, o mediante agentes SWE asincrónicos (LangGraph) o CLIs que pueden ejecutar código.
4. El Método A4F: La Estructura de 8 Puntos del Máster Prompt
Para forzarnos a pensar como arquitectos, todo Metaprompt (la solicitud humana) es procesado por Gemini para generar un Máster Prompt (la delegación al Agente) que sigue esta estructura fundacional de 8 puntos:
* Global System Prompt (GSP): Nuestros parámetros y patrones como empresa (A4F) para desarrollar software (calidad, seguridad, FinOps).
* Project System Prompt (PSP): Los parámetros específicos del proyecto (stack tecnológico, repositorios, contexto de negocio).
* Open Source projects reference: Links a repositorios (MIT/Apache) que sirvan como inspiración o estándar.
* Key Papers: Artículos (Arxiv.org, 2023+) que provean el marco teórico o conceptual.
* Example: Un ejemplo de código concreto que ilustra el patrón de diseño o la lógica deseada.
* Previous Code: El código existente, documentos adjuntos, HUs, o cualquier contexto previo relevante.
* Challenge Prompt: La definición explícita del problema, los componentes a desarrollar, el foco de valor y las restricciones.
* Bases para futuras evoluciones (V2.0): Pistas sobre cómo la solución debe escalar o evolucionar.
